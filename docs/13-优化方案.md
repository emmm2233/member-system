## 一、P0 —— 资金与审计（建议立即修，共约 1.5 人日）

### P0-1 资产调整的幂等键「前端发了，后端没接」🔴

**证据链**：

```
前端  web-admin/src/api/index.ts:297
      adjust: (data) => http.postIdem('/admin/accounts/adjust', data)
      request.ts:181  headers: { 'X-Idempotency-Key': idemKey || newIdempotencyKey() }
      → 请求头确实发出去了

后端  AccountController @PostMapping("/adjust")   ← 没有 @Idempotent
      → 请求头被 Spring 完全忽略（消费它的是 IdempotentAspect）

服务层 AccountService.adjust()
      String bizNo = noGenerator.custom("ADJ");   ← 每次调用生成全新单号
      .idempotencyKey(bizNo)
      → 唯一索引 uk_idem(idempotency_key, biz_type) 永远不冲突
```

**后果**：运营在「资产调整」弹窗点两下，或网络超时后重试一次，**余额/赠送/积分就被调两次**。
这类误操作在真实门店里一定会发生（调整往往伴随客诉，操作员本就紧张）。

**为什么危险等级高**：它绕过了本项目最核心的设计原则「资产变动必须可幂等重放」，
而项目此前已经修过 4 个同类资金级缺陷 —— 这是第 5 个，只是藏在「前端看起来做了」的假象里。

**修复方案**（两种，推荐 A）：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | `AccountAdjustCmd` 增加 `idempotencyKey` 字段；控制器加 `@Idempotent(prefix="account-adjust")`；服务层 `bizNo` 优先取入参的幂等键，缺省才自造 | 与收银/充值路径完全一致，改造面小 |
| B | 只加 `@Idempotent`，服务层不动 | 能挡住「同一次点击重复提交」，但挡住不了一次性令牌被换的情况（如前端重试生成新 key） |

**验收**：`round2-test` 加两条断言 —— 同一 `X-Idempotency-Key` 调两次 `/adjust`，
第二次必须返回 `10006 请勿重复提交`，且余额只变一次。

### P0-2 操作日志从未写入 —— 审计是空的 🔴

**证据**：全仓检索 `OpLog` 只命中两个文件：
- `modules/system/service/OpLogQueryService.java`（**读**）
- `modules/system/controller/SystemController.java`（**查**）

没有实体、没有 Mapper、没有切面、没有 `@OpLog` 注解；`m_op_log` **0 行**。
但「系统管理 → 操作日志」页面在菜单里，文档也写了「操作日志」。

**后果**：
1. **合规风险** —— 会员余额/赠送的调整、退单审批、手工发券这些动作无法追溯「谁在什么时候改的」；
2. 出问题时只能靠业务流水反推，而流水不带操作人（`m_balance_flow` 有 `operator_id`，
   但没有「操作人当时的角色/来源 IP/请求参数」）。

**修复方案**：
1. 新增 `OpLog` 实体 + `OpLogMapper`（表已存在，含 `module/action/target_id/params/ip/user_agent/status/cost_ms`）；
2. 新增 `@OpLog(module="资产", action="调整")` 注解 + AOP 切面，
   切**所有带 `@Idempotent` 的写接口 + 资产/退款/发券/权限变更**（约 30 个端点）；
3. 切面异步落库（`@Async` 或事件），**失败不影响主流程**，但要留 WARN；
4. 参数落库前脱敏（手机号、密码、密钥字段一律打码）。

**优先级理由**：这是「事后无法追责」类问题，发现的越晚，历史越补不回来。

### P0-3 幂等注解覆盖不统一（低风险但建议一次收口）

| 端点 | 现状 | 风险 |
|---|---|---|
| `POST /admin/accounts/adjust` | ❌ 无 | 见 P0-1 |
| `POST /admin/cards/{cardNo}/refund` | ❌ 无（靠卡状态机兜底） | 退卡有资金流出，重复调用会被状态校验挡住，但**没有明确的「重复提交」提示**，运营会以为失败而反复点 |
| `POST /admin/marketing/coupons/verify` | ❌ 无（靠券状态机兜底） | 同上 |
| `POST /admin/cashier/{orderNo}/refund`（申请） | ❌ 无（审批有） | 重复申请会产生多条待审批退单 |

**方案**：按「**凡是会产生资金/资产副作用或生成待办单据的 POST，一律加 `@Idempotent`**」统一收口，
并在 `@Idempotent` 上补一个 `checkIdempotentHeaderOnly=false` 之类的开关（当前实现默认如何取键需确认）。
把这条写进 [06-工程结构与实施计划](../docs/06-工程结构与实施计划.md) 的编码铁律。

## 二、P1 —— 性能与容量（上量前必须做，共约 2 人日）

> 说明：当前是开发库（19 会员 / 14 订单），**任何查询都是毫秒级**，所以这里不提供耗时数据，
> 结论全部来自**索引结构分析**与**查询可索引性判断** —— 这些在数据量上来后必然暴露。

### P1-1 业绩报表缺 `paid_at` 索引 🟠（本轮新引入，优先修）

**证据**：

```
m_order 现有索引： idx_staff_time = (staff_id, created_at)
                   idx_status_time = (status, created_at)
                   ⋯ 全部以 created_at 结尾
m_order 是否有 paid_at 索引： NO
```

而本轮的业绩查询是：

```sql
-- StaffPerformanceService.ranking（跨全部员工）
FROM m_staff s LEFT JOIN m_order o
     ON o.staff_id = s.id AND o.status IN (3,4,5)
    AND o.paid_at >= ? AND o.paid_at < ?
-- DashboardService.staffRanking 同理
```

`paid_at` 既不在索引里，也不在 `staff_id` 复合索引的第二列，
所以**排行查询会扫全表 m_order**。单员工明细能用 `staff_id` 等值过滤，问题较小。

**方案（二选一，推荐 A）**：
- **A**：新增 `idx_staff_paid (staff_id, paid_at)` + `idx_status_paid (status, paid_at)`；
- B：把业绩口径改回 `created_at` 复用现有索引 —— **不推荐**，
  「业绩以收款时间为准」是业务语义，不该为了省索引而妥协。

⚠️ 注意：改口径或加索引都要同步更新 [12-实施记录-第四轮 §2.1](../docs/12-实施记录-第四轮.md) 的口径说明，
避免下一轮有人以为两者可以互换。

### P1-2 生日扫描不可索引 🟠

```sql
-- MemberMapper.selectByBirthdayMonthDay
WHERE deleted = 0 AND status = 1
  AND DATE_FORMAT(birthday, '%m-%d') = #{monthDay}   -- ← 函数作用在列上，索引失效
```

`idx_birthday (birthday)` 存在但用不上。**每天 08:00 全表扫一次 `m_member`**。
10 万会员时这是一次全表扫 + 10 万次函数计算。

**方案**：加**生成列 + 索引**（MySQL 8 支持，对应用完全透明）：

```sql
ALTER TABLE m_member
  ADD COLUMN birthday_md char(5) GENERATED ALWAYS AS (DATE_FORMAT(birthday,'%m-%d')) STORED,
  ADD INDEX idx_birthday_md (status, deleted, birthday_md);
```

查询改为等值匹配即可走索引；**Java 侧一行不用改**（改 SQL 条件即可）。

### P1-3 看板缓存配置形同虚设 🟠

`m_sys_config.report.dashboard_cache_seconds = 600`，
`ConfigService.dashboardCacheSeconds()` 有 getter —— 但**全仓没有任何调用方**。
看板 9 类报表（含 RFM、留存、负债）每次打开都全量计算。

**方案**：在 `DashboardService` 的聚合方法上套 `CacheService`（键含 `storeId + days + 日期`），
TTL 取 `dashboardCacheSeconds()`；并在收银结算/退单/充值成功后**主动失效**
（复用已有的 `ConsumeCompletedEvent`，加一个监听器即可，成本很低）。

### P1-4 N+1 查询 🟠

| 位置 | 问题 | 量级 |
|---|---|---|
| `StoreService.toVo` | 每行 5 次 `COUNT`（在职员工/全部员工/订单/会员/账号） | N 家门店 → 5N+1 次查询 |
| `LevelAdminService:66` | 每个等级查一次会员数 | 等级数 N → N+1 |
| `BirthdayGiftService:415` | 每条发放记录查一次会员 | 分页 20 条 → 20 次 |
| `DashboardService:219` | 沉睡会员逐条查会员 | 同上 |

**方案**：统一改为「**先收集 id → 批量查 → Map 回填**」。
`StaffService.page` 已经是这个写法（批量查门店名与账号），照它改即可。
门店列表的 5 个计数改成一条 `GROUP BY store_id` 的聚合查询。

### P1-5 深分页与流水表增长 🟡

- 所有分页都是 `LIMIT offset, size`。`m_balance_flow` 在 100 万行时，
  翻到第 5000 页会扫 10 万行再丢弃。**账务流水页建议改游标分页**（`id < lastId`）。
- `m_balance_flow` / `m_point_flow` / `m_growth_flow` / `m_payment_notify_log`
  **没有任何归档策略**。按门店日均 300 单估算，3 年约 33 万单 → 流水 100 万+ 行。
  **方案**：加一个归档任务，把 N 年前的流水迁到 `*_archive` 表（同结构），
  对账与报表只查热表；归档前必须校验「归档前后余额恒等式仍成立」。

## 三、P2 —— 健壮性与可运维（共约 2.5 人日）

### P2-1 ShedLock 未真正启用 🟠

pom 里有 `shedlock-spring` + `shedlock-provider-jdbc-template`，
5 个 Job 类的**注释**里都写了「多实例部署需启用 ShedLock」，
但**没有 `@EnableSchedulerLock`、没有 `@SchedulerLock`、没有 `shedlock` 表**。

**这意味着当前系统只能单实例部署** —— 一旦起第二个实例：

| 任务 | 重复执行的后果 |
|---|---|
| 生日礼发放 | 唯一索引挡住重复发放 ✅ 但会重复扫描、重复发消息尝试 |
| 推荐奖励重试 | 条件 UPDATE 挡住重复发奖 ✅ |
| 等级批量重算 | **会重复全量重算**（无幂等保护），高峰期 CPU 翻倍 |
| 支付超时关单 / 掉单补偿 | 重复关单无副作用，但会对渠道重复请求 |
| 券/积分过期 | 重复扫描，且 `expireBatch` 的游标可能交错 |

**方案**：加 `@EnableSchedulerLock` + 每个 `@Scheduled` 上 `@SchedulerLock(name=..., lockAtMostFor=...)`，
建 `shedlock` 表（Flyway V7）；`lockAtMostFor` 要大于任务最长耗时（建议 30 分钟，并配 `lockAtLeastFor` 防抖）。

### P2-2 缓存仍是 Caffeine —— 多实例的根因 🟠

`CacheService` 有两套实现（Caffeine / Redis），当前用 Caffeine（本机无 Redis）。
但缓存里放的不只是「性能数据」，还有**正确性数据**：

| 缓存内容 | 多实例下的问题 |
|---|---|
| `loginuser:ADMIN:{id}` | 改权限后另一实例仍是旧权限（5 分钟窗口） |
| `seq:*` 业务序列号 | **两个实例会生成相同单号**（有 `generateWithRetry` 兜底，但会退化为重试） |
| `login:fail:*` 登录失败计数 | 5 次锁定在实例 A，请求打到实例 B 就不计数了 → **锁定失效** |
| `idem:*` 幂等键 | 幂等只在本实例生效 → **跨实例重复提交挡不住** |
| 微信 access_token | 各实例各取一次，微信侧会互相顶掉 |

**结论**：**Redis 不是「性能优化」，而是多实例部署的正确性前提。**
P2-1 与 P2-2 必须一起做，否则「加了 ShedLock 但幂等跨实例失效」比单实例更危险。

### P2-3 无限流 🟡

`TOO_MANY_REQUESTS(10005)` 定义了但全仓无使用。登录有失败锁定（已实现 ✅），
但 `/api/mp/**`（会员端，公网可达）无任何频次限制 —— 动态核销码校验、
`/api/mp/messages/subscribe/report` 这类接口可被刷。

**方案**：基于 `CacheService` 加一个简单的令牌桶/计数限流注解（如 `@RateLimit(key, qps)`），
优先保护 `/api/mp/**` 与 `/api/open/**`（支付回调）。

### P2-4 前端产物分包 🟠

```
dist 总计 3.1 MB
index-BflQPO4d.js  1246 KB
index-BVQ-WQ1n.js  1021 KB    ← 两个 chunk 各超 1 MB
```

Element Plus 已在用 `unplugin` 按需引入（`el-xxx.css` 分散产出证明了这点），
超大的两个 chunk 主要是 **ECharts 全量引入** + **Element Plus 全量图表/组件**。

**方案**：
1. `vite.config.ts` 配 `build.rollupOptions.output.manualChunks`，把
   `echarts` / `element-plus` / `vue` 拆成独立 chunk（利用浏览器并行与长效缓存）；
2. ECharts 改**按需引入**（`echarts/core` + 只注册用到的 chart/component）；
3. 看板页与图表组件用 `defineAsyncComponent` 懒加载 —— 非图表页不该加载 ECharts。

预期：首屏 JS 从 ~2.3 MB 降到 ~600 KB 量级。

### P2-5 WEB 类型错误基线 49 个 🟡

49 个错误全是同一个模式：Element Plus 表格作用域插槽给的是 `DefaultRow`，
传给业务类型参数报 `TS2345`。本轮为了不扩大基线，新页面统一用了 `(row: any)` + 函数内收窄。

**方案**：与其继续打补丁，不如一次性收口 —— 加一个类型工具：

```ts
// src/types/table.ts
export type Row<T> = T & Record<string, unknown>
// 用法：<template #default="{ row }: { row: Row<StaffRow> }"> 或统一封装 <DataTable> 组件
```

或引入一个薄封装的 `<DataTable :data :columns>` 组件，把插槽类型收敛掉。
**做完把 `npm run type-check` 加进 CI，基线归零并禁止回涨。**

### P2-6 没有 CI，且 396 项全是 API 冒烟 🟡

现状：8 套自检脚本必须**人工按顺序跑**（用 `run-all-tests.ps1`），且**强顺序依赖**
（后面的轮次复用前面创建的会员）。没有任何单元测试。

**真正的空白**（冒烟测不到，但这套系统最该测的）：
- **并发测试**：三层幂等（幂等键 / 唯一索引 / 行锁）声称能防并发，但 396 项里**没有一项是并发发起**的；
- **边界金额**：0.005 元四舍五入、满减券金额刚好等于应付、积分抵扣到上限 +1 分；
- **口径回归**：买了退、退了买之后余额/积分/成长值恒等式仍成立（现有测试只覆盖单次）。

**方案**：
1. **CI**：GitHub Actions / 本地 pre-push 钩子跑 `run-all-tests.ps1`（已在做前置依赖检查）；
2. **并发用例**：给 `money-chain-test` 加 3 条 ——
   用 PowerShell 的 `ForEach-Object -Parallel` 同时发 5 个同幂等键请求，
   断言「成功 1 个 + 失败 4 个 + 余额只变一次」；
3. **单元测试**：优先补 3 个纯函数 —— `MoneyUtil`、`CashierService.calculate`（金额链）、
   `StaffPerformanceService` 的汇总口径。这三处是「算错了没人看得出来」的地方。

## 五、建议执行顺序

按「**先止血、再扩容、后提速**」分四批：

| 批次 | 内容 | 工作量 | 为什么排这里 |
|---|---|---|---|
| **第 1 批** | P0-1 资产调整幂等、P0-2 操作日志落库、P0-3 幂等收口 | ~1.5 人日 | 资金与审计，**不修就是定时炸弹**；且改动面小、风险低 |
| **第 2 批** | P1-1 `paid_at` 索引、P1-2 生日生成列、P1-4 N+1 | ~1 人日 | 只是一次 Flyway + 几处查询改写，收益确定 |

## 六、明确不建议做的事（避免过度优化）

| 想法 | 为什么不建议 |
|---|---|
| 把单体拆成微服务 | 单品牌多门店的量级（预估 10 万会员 / 日均千单）单体完全够；拆了只会把事务一致性变成分布式难题，而本项目全部价值都在「资金一致性」上 |
| 引入 Elasticsearch 做会员搜索 | 会员检索是「手机号/会员号精确 + 姓名模糊」，MySQL 索引足够；95% 的查询是精确匹配 |
| 上分库分表 | 同上。**先做 P1-5 归档**，热点表瘦下来比分片简单一个量级 |
| 用消息队列替换 `@TransactionalEventListener` | 当前事件都是 AFTER_COMMIT 同步执行，失败有定时任务兜底，语义已正确；换 MQ 会引入「消息重复/顺序」两个新问题 |
| 重写前端为 SSR | 管理端是内部系统，首屏 1 秒与 2 秒没有业务差别；分包（P2-4）就够了 |

## 七、需要你确认的取舍

1. **第 1 批（P0 资金+审计）是否立即执行？** —— 我建议直接做，这条没有取舍空间。
2. **`m_member_stat` 是修复还是废弃？** —— 修复要挂到消费事件上（约半天），
   废弃要删表 + 删 `MemberStat` 相关代码（约 1 小时）。取决于**看板是否打算用「30 天消费额」这类预聚合**：
   如果以后要按 30d 金额做人群圈选（发券向导的条件里已经有 `minTotalConsume`），建议修复。
3. **Redis 什么时候上？** —— 如果短期只单实例部署，P2-1/P2-2 可以推迟；
   但只要计划「不停机发布」或「多实例」，就必须先做，否则幂等与登录锁定会静默失效。
4. **P3 功能补齐的优先级** —— 会员合并 / 交接班 / 提成，哪个是门店最先要的？
