## 1. 环境适配（与设计文档的差异说明）

设计文档原计划用 Docker 起 MySQL + Redis。实际执行时探测到：

| 项 | 设计预期 | 实际情况 | 采取的方案 |
|---|---|---|---|
| Docker | 可用 | **未安装** | 改用**本机已装的 MySQL 8.4.9**（服务已运行，端口 3306） |
| MySQL | Docker 容器 | 本机 `C:\Program Files\MySQL\MySQL Server 8.4`（root/123456） | 直连本机，`application-local.yml` 默认配置 |
| Maven | 需安装 | 未安装（仅有 `.m2/repository`） | 下载**便携版 Maven 3.9.9** 到 `tools/`（`scripts/install-maven.ps1`），不污染系统 |
| Redis | 必需 | **本机没有，也无 Docker** | 抽出 `CacheService` 接口：默认 **Caffeine 本地实现**（单机可跑），生产切 `member.cache.type=redis` |
| JDK / Node | — | JDK 21.0.11 ✅ / Node v24.14.1 ✅ | 直接使用 |

> **结论**：本机环境零额外安装即可运行完整后端；Redis 通过配置切换，不阻塞开发。

### 2.5 后端 · 资产账务（P1，资金核心）

- **`AccountService` 是系统内唯一允许变动资产的入口**（`modules/account/service/AccountService.java`）
  - 统一 `change(AccountChangeCmd)`：余额/赠送/积分/成长值四类资产可同时变动，流水与余额同事务
  - 行锁 `SELECT ... FOR UPDATE` + 乐观锁 version + SQL 层余额充足条件
  - 语义化封装：`recharge` / `consume` / `refundBalance` / `revokeRecharge` / `adjust` / `grantPoints` / `deductPointsForRefund` / `consumeSplit`
- **积分批次 FIFO**：获得写批次，扣减按到期时间从早到晚消耗，过期任务按批次处理并写流水
- 充值：`RechargeService`（方案赠送/送积分/送券、大额阈值、幂等、充值撤销）
- 查询与对账：`AccountQueryService`（余额/积分/成长值流水、积分批次、**对账**、负债汇总、单会员账实核对）

### 2.6 后端 · 收银结算与订单（P2）

- **`CashierService`**：实现设计文档 §3.1 的完整金额计算链
  1. 原价合计 → 2. 会员折扣（会员价优先）→ 3. 券抵扣（受门槛/封顶/叠加约束）→ 4. 积分抵扣（受最高抵扣比例与兑换比例约束）→ 5. 应收 → 6. 支付明细守恒校验 → 7. 获得积分（按明细分摊×品类倍率×等级倍率）→ 8. 获得成长值
  - **赠送余额抵扣部分不计积分与成长值**
  - 试算接口不落库，正式结算服务端重算（不信任前端）
- 余额支付按优先级拆分本金/赠送，**分别落两条支付明细**（退单时按来源原路退回）
- `RefundService`：退单申请/审批/冲正（退回余额、扣回积分与成长值、恢复券、回补库存、订单状态流转）
- 交接班汇总：按门店+日期汇总订单与各支付方式金额

## 4. 实施中发现并修复的资金级缺陷（重要）

这些是编码过程中通过自检暴露出来的真实缺陷，已修复并留档：

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | **本金与赠送流水共用同一幂等键** | `uk_idem(idempotency_key, biz_type)` 冲突 → **只要充值带赠送金额就整单失败** | 幂等键按账户类型加后缀（`:P` / `:G`） |
| 2 | **退单未区分本金/赠送来源** | 用 `min(退款额, 余额支付额)` → 赠送支付的钱会被退成本金（资金性质错误） | 余额支付按来源拆两条 `m_order_payment`（`account_type`），退款按比例原路退回 |
| 3 | **对账口径把 status=1 作为过滤条件** | 批次被扣空（status=2）时产生**假差异告警** | 改为统计全部批次 `remain_points`（终态已为 0） |
| 4 | **`AccountService.validate` 对负值参数报错** | 消费扣减传负值被 `requireNonNegative` 拦下 → **收银结算完全不可用** | 校验改为取绝对值（校验"大小"而非符号） |
| 5 | 单号序列在重启/清库后与库重叠 | 会员号/订单号唯一键冲突 | ① 启动时按库恢复水位 ② 生成时校验 `m_order.order_no` **与流水幂等键**后重试 |
| 6 | 幂等切面拒绝"未带幂等键"的合法调用 | 收银台/第三方调用易失败 | 未传时服务端生成键，真正的防重由数据库唯一索引 + 入账幂等键兜底 |
| 7 | 充值接口返回的账户快照漏掉赠送积分 | 前端展示"送 200 积分但积分为 0" | 赠分/赠券后重新读取账户并补充 `pointsAfter/balanceAfter/giftBalanceAfter` |
| 8 | 初始 admin 密码哈希无效 | 无法登录 | 用 `BCryptPasswordEncoder` 生成 `Admin@123` 的正确哈希并同步到 DDL |

**过程性事故**：使用 PowerShell 的 `-replace`/`Set-Content` 处理 SQL 文件导致中文被编成 GBK 乱码（`主键`→`涓婚敭`）。已改为**只用 Node 脚本处理 UTF-8 文件**（`scripts/normalize-sql.js`），并加了乱码检测。

## 5. 与原设计的偏差与取舍（需知悉）

| 项 | 设计 | 实现 | 原因 |
|---|---|---|---|
| Redis | 必需 | **可选**（默认 Caffeine） | 本机无 Docker/Redis；抽象成 `CacheService`，生产切配置即可 |
| 分布式锁 | Redis SETNX | 内存 SETNX + 数据库唯一索引兜底 | 单实例部署下等价；多实例前需切 Redis 实现 |
| 定时任务锁 | ShedLock | Spring `@Scheduled`（依赖已引入未启用） | 单实例部署；多实例时加 `@SchedulerLock` 即可 |
| 挂单/取单 | P2 完整实现 | **未实现**（前端给出明确提示） | 需 `m_order` 挂单态 + 状态流转，已排入下一阶段 |
| 会员导入导出 | P2 | **未实现** | 同上 |
| 次卡售卡/核销 | P2 | **未实现**（表结构与设计已就绪） | 同上 |
| 券模板管理页 | P4 | 后端提供查询/发放/核销/统计接口，**管理页面未做** | 同上 |
| 小程序端 | P5 | **未开始** | 本轮聚焦 P0~P2 + 支付预留 |
| 看板报表 | P6 | 工作台为简版（负债+对账+当日汇总） | 完整看板排入后续 |

## 6. 如何运行与自检

```powershell
# 1) 安装便携 Maven（已安装可跳过）
powershell -ExecutionPolicy Bypass -File scripts/install-maven.ps1

# 2) 构建后端
cd backend
..\tools\apache-maven-3.9.9\bin\mvn.cmd -DskipTests package

# 3) 重置数据库（可选，Flyway 会自动建表）
powershell -ExecutionPolicy Bypass -File ..\scripts\reset-db.ps1 -Yes

# 4) 启动后端（前台运行，Ctrl+C 停止）
java -jar target/member-system.jar --spring.profiles.active=local
#    健康检查 http://127.0.0.1:8080/actuator/health
#    接口文档 http://127.0.0.1:8080/swagger-ui.html

# 5) 端到端自检（另开终端）
powershell -ExecutionPolicy Bypass -File scripts/smoke-test-ascii.ps1     # 基础功能 12 项
powershell -ExecutionPolicy Bypass -File scripts/money-chain-test.ps1     # 资金链路 28 项

# 6) 启动 WEB 管理端
cd web-admin
npm install
npm run dev        # http://127.0.0.1:5173  账号 admin / Admin@123
```

## 8. 结论
