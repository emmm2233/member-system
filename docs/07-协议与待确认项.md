## F. 评审检查清单（逐项打勾即可确认）

**业务正确性**
- [ ] 资产模型（本金/赠送/积分/成长值 四账分离）符合你的业务
- [ ] 金额计算链（原价→等级折扣→券→积分→应收）顺序与规则正确
- [ ] 赠送抵扣部分不计积分与成长值 —— 是否符合你的预期（这是防刷等级的关键）
- [ ] 退单规则（只退本金、扣回积分、券退回）符合预期
- [ ] 混合支付退单规则（A16：余额原路退、现金线下退）符合财务习惯
- [ ] 商品库存是否参与扣减（A17）—— 若需要，属新增范围
- [ ] 等级评定依据（默认累计成长值）与门槛值（1000/3000/8000/20000）是否需要调整
- [ ] 推荐有礼仅一级、触发条件为首单 ≥ 50 元 —— 是否合规且符合营销预期
- [ ] 会员合并流程（人工审核 + 资产转移规则）是否接受
- [ ] 次卡与储值卡的边界（次卡不占用储值余额）是否清晰

**数据与接口**
- [ ] 47 张表覆盖了你的全部业务场景（有无遗漏：如预约、员工提成、库存？）
- [ ] 索引与分页策略能否支撑你预期的数据量（会员数？日订单数？）
- [ ] 约 197 个接口是否覆盖两端全部页面需求
- [ ] 错误码与统一响应体是否符合你团队既有规范
- [ ] **支付预留方案（`IPayChannel` + 支付单 + 回调日志 + 22 个接口 + 小程序支付页）是否满足后续接入预期**（见 [08-支付接口预留与启用方案](./08-支付接口预留与启用方案.md)）
- [ ] 支付只做"在线充值"是否够用，售卡/积分兑换是否也要在线支付

**技术与交付**
- [ ] 技术选型（MyBatis-Plus / Spring Security / uni-app / Element Plus）无异议
- [ ] 单机 + Docker 的部署方式可接受
- [ ] 实施节奏（P0~P7，约 39 人日）与你的时间预期一致
- [ ] 风险登记册中的 R1（资金台账差异）、R8（断网无法收银）应对策略可接受
