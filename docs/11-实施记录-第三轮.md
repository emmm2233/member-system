## 1. ① 挂单 / 取单

`modules/cashier/service/HoldOrderService.java`

| 能力 | 说明 |
|---|---|
| 挂单 | 复用 `m_order.status=7`（STATUS_HOLD），不新建表 |
| 购物车快照 | 序列化进 `m_order.remark` 的 `[CART:[...]]` 段 |
| 取单 | `resume(holdNo)` 还原购物车，**条件 UPDATE 抢占**（`WHERE status=7`），第二次取单必然失败 |
| 弃单 | `cancel(holdNo, reason)` 置为已取消 |
| 超时清理 | `cleanExpired(limit)` 分批扫描，由定时任务调用 |

**关键坑（已修）**：`remark` 里可能同时存在其它说明文字，早期实现用 `indexOf(']')` 找购物车 JSON 的结束位置，
遇到嵌套数组（商品项本身是数组）会被提前截断，反序列化报
`Unexpected end-of-input: expected close marker for Array`。
现改为**括号深度配对**扫描，找到与 `[CART:` 的 `[` 真正匹配的 `]`。

> 挂单**不动任何资产**：只是把购物车寄存，不产生流水、不锁券、不扣积分（`round3-test` 有专门断言）。

## 4. ③ 推荐有礼

### 4.1 设计：三个动作，三段职责

| 动作 | 入口 | 关键机制 |
|---|---|---|
| **绑定** | `ReferralService.bind()` | 防刷校验链 + `m_referral.invitee_id` 唯一索引兜底 |
| **结算** | `ReferralService.settleIfEligible()` / `settle()` | 条件 UPDATE 抢占结算权（`WHERE status=1`），抢占失败者不得发奖 |
| **发奖** | `ReferralService.issueRewards()` / `issueOne()` | 先落 `m_referral_reward`（待发放）再调资产服务；资产幂等键 `REF:{关系ID}:{对象}` |

**为什么结算与发奖必须分开事务**：结算标记一旦落库就不能回退（否则可能重复发奖），
而发奖可能因券模板下架、账户冻结等临时原因失败。分开之后，失败的奖励留在库里，
由两个补偿入口自愈。

### 4.2 邀请码：可逆、不可伪造、无需码表

```
邀请码 = base36(memberId) + HMAC-SHA256(secret, base36)[0..4)
校验位字符集去掉 0 O 1 I 等易混字符
```

- **不落库**：解析是纯计算，没有码表可被遍历；
- **不可伪造**：改任何一个字符都会导致校验位不匹配（1/32⁴ ≈ 百万分之一碰撞）；
- **可运维**：`referral.invite-secret` 可轮换（轮换后所有旧码立即失效，活动期间勿改）。

### 4.3 防刷校验链（任一条不满足即拒绝）

```
1. 活动已开启
2. 邀请码合法（签名校验通过）
3. 不能填自己的邀请码
4. 被推荐人状态正常
5. 邀请人存在且状态正常
6. 被推荐人未绑定过邀请人（member.referrer_id + m_referral 双查）
7. 被推荐人已绑手机号（可配 referral.require-phone）
8. 邀请人与被推荐人手机号不同（防小号自荐）
9. 绑定窗口内（注册后 N 天内，referral.bind-window-days）
10. 邀请人必须是「老会员」（注册时间不晚于被推荐人）
```

**月度上限只限制推荐人侧**：超出 `referral.max-per-referrer-month` 时，
推荐人侧记一条「发放失败 + 原因」留痕，被推荐人奖励照发 ——
新人不应为推荐人的刷单行为买单。

### 4.4 「首单」判定的坑

```sql
-- 曾经的做法：WHERE status = 3（已支付）
-- 问题：一笔已退款的订单会让「首单」永远成立 → 重复发奖
SELECT COUNT(*) FROM m_order
 WHERE member_id = ? AND order_type = ? AND status IN (3,4,5)   -- 3已支付 4部分退款 5已退款
```

即「曾经支付成功过」的订单都算数，用 `count == 1` 判定首单。

### 4.5 三道补偿（`ReferralJob`）

| 时间 | 任务 | 覆盖的失败面 |
|---|---|---|
| 04:10 | `settleByScan` | 事件丢失（进程重启 / 监听器异常 / 事务提交后崩溃）→ 用订单数据反推是否已达成条件 |
| 04:20 | `retryPendingRewards` | 券模板临时下架、账户冻结等瞬时故障 |
| 04:30 | `reconcileSettled` | 「结算标记已提交、进程在发奖前挂掉」的极端窗口 → 补建缺失奖励 |

## 5. ③ 生日礼

`modules/birthday/` —— 表 `m_birthday_gift_log`，(member_id, gift_year) **唯一索引**。

### 5.1 为什么要单独一张发放日志表

资产层的幂等键只能保证「不重复加钱」，**不能保证不重复发券、不重复发消息**，
也无法回答运营的问题「这个会员今年到底领没领、领了什么」。
`(member_id, gift_year)` 唯一索引是「一年只送一次」的**唯一真相来源**。

### 5.2 年份语义

`gift_year` 取「这次生日礼对应的那个生日的年份」。若配置提前 7 天发放，
12 月 30 日的会员会在次年 1 月 6 日收到礼，归入次年 ——
与会员「我今年收到过生日礼了」的认知一致。

### 5.3 闰日处理

2 月 29 日出生的会员在平年没有生日。当目标日是 2 月 28 日且当年不是闰年时，
额外扫描 `02-29`，让这些人也在 2 月 28 日收到生日礼，而不是被系统悄悄遗忘。
小程序端的「距生日天数」同样做了降级（闰日按 2/28 算，不会算出 366 天）。

### 5.4 生日字段的年份常是占位

建档时客户不愿透露年龄，年份常填 `1900`。因此匹配用
`DATE_FORMAT(birthday,'%m-%d') = ?` 而不是比较完整日期 —— 后者会一个人都匹配不上。

### 5.5 部分失败可修复

先落一条「部分发放」的占位记录再逐项发放（积分/余额/成长值/券），
任一项失败都留在记录里；`repairFailed` 会重跑未完成的项，
而资产层幂等键保证已成功的项不会被加第二次。

定时任务：08:00 发放（不选凌晨 —— 凌晨的祝福容易被当成骚扰消息屏蔽）、09:30 修复。

### 5.6 接口

```
GET  /api/admin/birthday/stats        概览（本年度已发/部分/失败/今日生日数）
GET  /api/admin/birthday/config       规则配置项
POST /api/admin/birthday/config       保存规则（券模板必须真实存在且启用）
GET  /api/admin/birthday/preview      按 MM-dd 预览将发放名单（不实际发放）
GET  /api/admin/birthday/logs         发放记录分页
POST /api/admin/birthday/issue        手动发放/补发单个会员
POST /api/admin/birthday/tasks/issue  手动触发批量发放
POST /api/admin/birthday/tasks/repair 手动触发失败修复

```

## 6. ④ 消息中心与订阅消息

`modules/message/` —— 表 `m_message_tpl`（模板）、`m_message_record`（记录）、`m_message_subscribe`（授权额度）。

### 6.1 三条不变量

1. **幂等**：`m_message_record.idempotency_key` 唯一索引。同一业务动作（同一笔生日礼、
   同一笔推荐奖励）重复调用只会得到同一条记录，不会给用户发两条。
2. **不丢内容**：模板渠道不可用时**降级为站内信**，用户在小程序「消息中心」仍能看到完整内容，
   记录里留下降级原因。
3. **不阻断主链路**：`sendQuietly` 吞掉一切异常，收银/发奖事务不受消息影响。

### 6.2 渠道抽象

```java
public interface MessageChannel {
    String code();                 // INNER / WX_SUBSCRIBE / SMS(预留)
    String name();
    boolean available();           // 必须是无副作用的快速判断
    String unavailableReason();
    SendResult send(MessageTpl tpl, MessageRecord record);
}
```

`MessageChannelRegistry` 在启动时收集所有实现 —— 新增渠道（短信、公众号模板消息、企微）
只需加一个 `@Component`，业务侧零改动。

### 6.3 微信一次性订阅消息的额度语义

微信规则：**用户每授权一次，服务端只能下发一条**。因此不能只看「是否授权过」，
必须按模板维度记账剩余次数：

```
小程序 wx.requestSubscribeMessage → 上报接受的模板 ID → m_message_subscribe.remain_count + 1
每次真正下发前 → 条件 UPDATE 预扣（WHERE remain_count > 0）→ 扣不到则降级站内信
下发失败（非用户拒收）→ 归还额度，下次重试仍有额度
```

条件 UPDATE 是并发安全的：多个线程同时下发只有一个扣成功，
不会出现「授权 1 次却发出去 3 条」的越权触达。

### 6.4 微信字段映射

微信订阅消息的 data 字段名由模板决定（`thing1`/`amount2`/`date3`…），
长度还有上限（thing 约 20 字，超长整条被拒）。
因此 `m_message_tpl.wx_data_map` 存映射 JSON，系统按字段前缀自动截断：

```json
{"thing1":"{memberName}","amount2":"{amount}"}
```

### 6.5 接口

```
GET  /api/admin/message/tpls                    模板列表（含占位符解析结果）
PUT  /api/admin/message/tpls/{id}               编辑模板（校验 wx_data_map 合法性）
GET  /api/admin/message/channels                渠道就绪状态（微信是否可用 + 原因）
GET  /api/admin/message/records                 发送记录分页
POST /api/admin/message/records/{id}/resend     手动重发
POST /api/admin/message/records/retry           手动触发失败批次重试

GET  /api/mp/messages                           小程序：消息中心
GET  /api/mp/messages/unread-count              未读数
POST /api/mp/messages/{id}/read                 标记已读
POST /api/mp/messages/read-all                  全部已读
POST /api/mp/messages/subscribe/report          上报订阅授权
GET  /api/mp/messages/subscribe/quota           我的订阅额度
```

权限码：`message:tpl:list`、`message:tpl:edit`、`message:record:list`、`message:record:resend`。

## 7. ④ 微信支付渠道骨架（APIv3）

`modules/payment/channel/wechat/`

| 文件 | 职责 |
|---|---|
| `WechatPaySigner.java` | 请求签名 / 应答验签 / 回调解密 / PEM 解析 —— **资金安全关键路径，单独成类以便测试** |
| `WechatPayConfig.java` | 商户参数读取 + 就绪判定 + 本地自检（不联网） |
| `WechatPayClient.java` | HTTP 客户端（JSAPI 下单/查单/关单/退款/下载平台证书） |
| `WechatPayChannel.java` | 实现 `PayChannel` + `DiagnosableChannel` |

### 7.1 就绪判定不只看「填没填」

`missingConfigs()` 做**值校验**而非仅非空校验：

```
商户号 / 商户证书序列号 / AppID / 32位APIv3密钥 / 可解析的商户私钥 / HTTPS 回调地址
```

私钥格式错、APIv3 密钥不是 32 位、回调地址不是 HTTPS —— 都属于「配了但没用」的情况，
必须在管理端就暴露，而不是等第一笔真实支付失败。

### 7.2 本地自检：私钥自签自验

自检不只验证「私钥能解析」，而是**从私钥推导出公钥做一次真实的签验**：
CRT 形式的 RSA 私钥带有 modulus 与 publicExponent，足以构造公钥。
这样能一次性排除「私钥与商户证书不匹配」「私钥被截断」「复制时带上了多余字符」
这些只有到真实下单才会暴露、且错误信息极不友好的问题。

**刻意不做网络调用** —— 自检要能在没有外网、微信接口抖动时随时跑。

### 7.3 缓存键必须带配置指纹（已修的真实缺陷）

早期版本用固定缓存键缓存解析后的私钥，导致「换了私钥但解析结果还是旧的」：
**自检报通过、真实下单却签名失败**。现改为 `wxpay:privatekey:{hash(配置值)}`，
平台证书同理。

### 7.4 回调安全

```
1. 校验 Wechatpay-Timestamp 与当前时间偏差 ≤ 300 秒（防重放）
2. 用平台证书公钥验证 timestamp\nnonce\nbody\n 的签名
3. 验签通过后才解密 resource（AES-256-GCM）—— 顺序不能反，
   否则等于给了攻击者一个免费的解密 oracle
4. 金额一致性校验：回调金额必须与本地支付单一致（防金额篡改）
```

平台证书优先用 `pay.wechat.platform-cert` 手工配置；
未配置时通过 `/v3/certificates` 自动下载并按序列号缓存 6 小时，
回调头里的 `Wechatpay-Serial` 对不上时会**强制刷新一次**
（覆盖「证书刚轮换、缓存还是旧的」这一必然发生的场景）。

## 9. 本轮踩到并修掉的坑

### 9.1 `INSERT ... ON DUPLICATE KEY UPDATE` 被 BlockAttack 拦截

订阅授权额度原本用单语句 upsert：

```sql
INSERT INTO m_message_subscribe (...) VALUES (...)
ON DUPLICATE KEY UPDATE remain_count = remain_count + 1
```

执行时报 `java.lang.UnsupportedOperationException`，**异常信息为空**，排查成本极高。
栈底指向 `com.baomidou.mybatisplus.extension.parser.JsqlParserSupport.processInsert` ——
项目启用了 `BlockAttackInnerInterceptor`（防全表更新/删除），
其内置的 JSqlParser 版本解析带 `ON DUPLICATE KEY` 的 INSERT 时不支持。

**改为三步**：先 `UPDATE`，影响 0 行再 `INSERT`，撞唯一键则回头 `UPDATE`。语义等价、可移植。

### 9.2 消息渠道额度与降级的两处逻辑漏洞

- `buildData` 失败时提前 `return`，但**额度已经预扣且没有归还** → 把 `buildData` 移到扣额度之前；
- 非用户原因的失败必须归还额度，否则「微信抖动几次就把用户的授权次数烧光」。

### 9.3 PowerShell 单元素数组与 JSON

`@{ templateIds = @('x') } | ConvertTo-Json` 在 PS 5.1 下会正确输出 `["x"]`，
但**测试脚本必须用真实文件或 `[System.Text.Encoding]::UTF8.GetBytes()` 传 body**，
否则中文/引号会被 shell 吞掉（本项目早期已踩过 `10001 请求体格式不正确`）。

### 9.4 PS 5.1 读取无 BOM 的 UTF-8 脚本会按 ANSI 解析

自检脚本中的中文字符串会被解析成乱码并**破坏语法**（`Unexpected token`）。
因此不需要中文输出的 `scripts/*.ps1` **一律纯 ASCII**；
需要中文的脚本则必须写 UTF-8 + BOM。需要校验中文文案时，从接口读回原值再比对，
而不是把中文写进脚本。

### 9.5 无 BOM 的 .ps1 会**静默吃掉下一行代码**（含资金级断言）

第三轮收尾整理文件时的发现，比 §9.4 更隐蔽，值得单独记一笔。

`money-chain-test.ps1` 含 3 行中文注释（说明退单按资金来源原路退回），
文件是 UTF-8 但**没有 BOM**。PowerShell 5.1 按 ANSI（GBK）解码时：

```
注释行结尾：  … 退款不会凭空增加）。
                                       └─ '。' 的 UTF-8 字节是 E3 80 82
GBK 解码：    E3 80 → 一个汉字；剩下 82 与紧跟的换行 0x0A 拼成一个合法 GBK 双字节
结果：        换行被「吃掉」，下一行代码被并入注释
```

被吃掉的正是资金级断言 `Check 'principal restored to 600'`（退单后本金是否从 550 恢复为 600）。

**危害在于它是静默的**：脚本不报语法错误、不报 FAIL，只是少跑一条断言，
输出 `RESULT: PASS=28 FAIL=0` 看上去全绿 —— 退单后本金是否正确恢复**根本没被验证**。

| | 断言数 | 输出 |
|---|---|---|
| 无 BOM（修复前） | 28 | `PASS=28 FAIL=0` ← 假绿 |
| 有 BOM（修复后） | 29 | `PASS=29 FAIL=0` |

**处理**：给 4 个含中文却缺 BOM 的脚本（`money-chain-test.ps1`、`reset-db.ps1`、
`start-backend.ps1`、`install-maven.ps1`）补上 UTF-8 BOM，并逐个做语法检查。

**新增防线**：断言总数必须与脚本里的 `Check` 调用数一致，不等即有代码被吃掉。
七个脚本已核对一致（12/29/33/29/27/49/115）。规则与排查命令见
[scripts/README.md](../scripts/README.md)。

### 9.6 后台任务不要用 `Start-Process` 启动 JVM

以「后台作业」方式运行 `run-all-tests.ps1` 时，脚本内 `Start-Process` 启动的 java
是 PowerShell 的子进程；作业结束时整棵进程树被销毁，**端口 8080 直接失联**。
现改为通过 `Win32_Process.Create` 创建进程（父进程是 WMI provider，不在作业进程树内）。
