## 1. 第 1 批：资金与审计（P0）

### 1.1 P0-1 资产调整幂等：把「前端发了」变成「后端真的接住了」

| | 改造前 | 改造后 |
|---|---|---|
| `AccountAdjustCmd` | 无幂等键字段 | 新增 `idempotencyKey` |
| `AccountController#adjust` | 无注解，请求头被忽略 | `@Idempotent(prefix="account-adjust")` + `@OpAudit` + 请求头回落 |
| `AccountService.adjust` | 每次自造单号 → 唯一索引永不冲突 | 优先取入参幂等键，缺省才自造 |
| 幂等读侧 | 只查余额/积分流水 | **查三张流水表**（余额/积分/成长值） |

**为什么读侧要查三张表**：同一个幂等键可能落在任意一种资产流水上（调整本金、调整积分、
调整成长值），只查其中一张表会让另外两种「重复提交」漏过去。这里曾经漏掉成长值流水，
结果是 round6 出现 22 条 FAIL —— 补 V8 的 `uk_idem` 唯一索引后才真正闭环。

**验收证据**（round7）：同一 `X-Idempotency-Key` 连发两次，第二次必须返回
`10006 请勿重复提交`，且余额只变一次；换一个幂等键则正常再调一次。

### 1.2 P0-2 操作留痕：从「有表无写入」到「默认全记」

改造前 `m_op_log` **0 行**：有查询接口、有菜单页面、有文档，就是没有写入方。

**为什么选择 opt-out（默认全记）而不是逐个标注**：

```
全仓 106 个控制器写接口，改造前只有 8 个带 @Idempotent。
若按「加注解才记录」的思路，退单审批、次卡退卡、会员调级、RBAC 变更全部不留痕，
而且以后新增的接口会继续默认不留痕 —— 这是结构性的漏，不是疏忽。
```

所以 `OpAuditAspect` 的切点匹配**所有控制器上的 `@PostMapping/@PutMapping/@DeleteMapping`**，
只有显式 `@NoAudit("理由")` 才跳过（当前 22 个豁免，全部有理由：登录/刷新/预览/试算/
渠道回调/Mock 小票等「要么无副作用、要么已单独落表」的接口）。

三个刻意的设计决定：

| 决定 | 理由 |
|---|---|
| **同步写、不异步** | 异步要么丢日志（线程池打满），要么业务失败时来不及记「谁尝试过什么」。一次 INSERT 约 1ms，换确定性值得 |
| **失败也写** | 业务抛异常时记 `status=0 + errorMsg` 再原样抛出。「谁尝试改余额但失败了」和「谁改成功了」同样重要 |
| **绝不因为写日志而影响业务** | 落库包在 try/catch 里，失败只 WARN。审计表写不进去，不该让收银结不了账 |

执行顺序也是刻意的：切面优先级 `200`（比幂等切面的 `100` 更靠内），
被幂等挡下的重复请求不会产生审计记录 —— 否则运营连点几下就把日志表刷满，真正的操作反而被淹没。

**踩过的坑（值得单独记）**：最初写成
`@annotation(opAudit) || @annotation(idempotent)` 并声明两个形参，启动直接失败：

```
java.lang.IllegalArgumentException: error at ::0 inconsistent binding
```

AspectJ 不允许「某个 `||` 分支绑定形参、另一个分支不绑定」。改为**切点只做匹配判断、
通知内部用 `sig.getMethod().getAnnotation(...)` 取值**，语义完全一样而且更简单。
（同一个坑在第 4 批又踩了一次，见 §4.5。）

### 1.3 P0-3 幂等收口 + 复核工具

新增 4 处 `@Idempotent`：卡退卡（`card-refund`）、券核销（`coupon-verify`）、
退单审批（`refund-approve`）、支付退款（`pay-refund`）。

统一口径写进代码注释与本文档：**凡是会产生资金/资产副作用、或生成待办单据的写接口，
一律加 `@Idempotent`**。

为了让这条口径不会随时间腐化，新增复核工具：

```powershell
node scripts\tools\audit-coverage.js --strict
# 控制器写接口总数: 107
#   默认留痕: 85（其中 38 个带中文标签）
#   显式豁免: 22
# [OK] 所有写接口均已留痕，豁免清单与基准一致
```

它做两件事：① 默认留痕覆盖率统计；② **豁免清单与基准逐条比对**（有人偷偷加一个
`@NoAudit` 会被 `--strict` 挡下）。豁免清单是「需要人工复核」的名单，不是垃圾桶。

## 2. 第 2 批：性能与容量（P1）

### 2.1 索引：怎么证明「真的会被用上」

开发库只有 20 会员 / 15 订单，`EXPLAIN` 说「走全表扫」是**优化器的正确选择**，
拿它当断言只会得到假失败。所以 round8 断言的是**可索引性（sargability）**，
这个结论与数据量无关：

```sql
-- 新谓词 + 强制走新索引 → type=ref/range，rows << 表行数
SELECT ... FROM m_order FORCE INDEX(idx_staff_paid)
 WHERE staff_id = 1 AND paid_at >= ? AND paid_at < ?;

-- 旧谓词 + 强制走同一索引 → type=index（全索引扫描），rows = 表行数
SELECT ... FROM m_order FORCE INDEX(idx_staff_paid)
 WHERE staff_id = 1 AND created_at >= ? AND created_at < ?;
```

两次对照的差异，正是「业绩口径用 `created_at` 时索引失效」这个缺陷本身。

V8 新增的索引：

| 表 | 索引 | 服务于 |
|---|---|---|
| `m_order` | `idx_staff_paid (staff_id, paid_at)` | 员工业绩排行 / 明细（口径是 `paid_at`） |
| `m_order` | `idx_store_paid (store_id, paid_at)` | 门店日报 / 趋势 |
| `m_payment_order` | `idx_status_created (status, created_at)` | 掉单补偿扫描（`status IN (1,2) AND created_at >= ?`） |
| `m_growth_flow` | `idx_biz`、`idx_member_time` | 成长值查询与对账 |

> 顺带修掉两个**断言自身的假失败**：`mysql -N` 会去掉列名导致按列名解析全空；
> `EXPLAIN` 多表 JOIN 时首行是驱动表、不是目标表。教训：解析 `EXPLAIN` 必须
> 显式取「表名匹配的那一行」，且要用 `-B`（带列名）而不是 `-N`。

### 2.2 生日扫描：生成列 + 索引

```sql
-- 改造前：函数作用在列上，idx_birthday 用不上 → 每天 08:00 全表扫 m_member
WHERE DATE_FORMAT(birthday, '%m-%d') = #{monthDay}

-- 改造后：等值匹配生成列，Java 侧一行没改，只改了 SQL 条件
ALTER TABLE m_member ADD COLUMN birthday_md char(5)
  GENERATED ALWAYS AS (DATE_FORMAT(birthday,'%m-%d')) STORED;
ALTER TABLE m_member ADD INDEX idx_birthday_md (status, deleted, birthday_md);
```

**一个反直觉的实测结论**：MySQL 8 的优化器会把「与生成列定义完全一致的表达式」
自动替换成生成列 —— 也就是说**旧写法的 SQL 也能走上新索引**（round8 里实测到了）。
所以这条修复的真正价值不是「让旧 SQL 变快」，而是让**索引意图显式化**：
查询里写 `birthday_md = ?` 时，任何人一看就知道走哪个索引，不必依赖优化器版本行为。

### 2.3 N+1 批量化（4 处）

| 位置 | 改造前 | 改造后 |
|---|---|---|
| `StoreService.toVo` | 每行 5 次 `COUNT` | `StoreMapper.countReferences` 一条 `UNION ALL` 批量计数 → `toVo(store, countMap)` |
| `LevelAdminService.list` | 每个等级查一次会员数 | `MemberMapper.countGroupByLevel` 一次 `GROUP BY` |
| `BirthdayGiftService` | 每条发放记录查一次会员 | `pageLogs` 先收集 id → `selectByIds` → Map 回填 |
| `DashboardService` 沉睡会员 | 逐条查会员 | 同上模式 |

### 2.4 连带的资金级修复：`m_growth_flow` 缺幂等键列

第 1 批做「幂等读侧查三张流水表」时才发现：`m_growth_flow` **既没有
`idempotency_key` 列，也没有对应唯一索引**，而代码已经在按它做幂等判断。
后果不是「查不到」而是「查询直接报 `Unknown column`」——
`settle` 全挂、money-chain 由 29 项掉到 19/4、round5 出现 23 条 FAIL、round6 出现 22 条 FAIL。

**这类问题的教训**：三层幂等（缓存键 + 唯一索引 + 行锁）里，**唯一索引是最后一道防线**，
它的存在与否必须能被自检发现，而不是等业务报错。V8 补齐列 + `uk_idem(idempotency_key, biz_type)` 后全绿。

## 3. 第 3 批：看板缓存与前端产物

### 3.1 看板读缓存：让 `report.dashboard_cache_seconds` 真的有调用方

改造前：这个参数有定义、有 getter、**没有任何调用方**，看板 9 类报表每次打开都全量算。

实现：`DashboardCache.get(key, loader)` 包住 `DashboardController` 的 8 类聚合查询，
键含门店/天数/日期，TTL 取配置值。

三个关键取舍：

1. **失效用「按前缀整体失效」而不是逐个维护依赖**：一笔消费会影响总览、趋势、RFM、
   留存、排行等多个指标，逐个维护依赖关系既复杂又容易漏。所以
   `CacheService.deleteByPrefix("dash:")` 一把清掉 —— 牺牲一点命中率换「不可能漏失效」。
2. **Redis 实现绝不用 `KEYS`**：`KEYS pattern` 会遍历整个键空间并阻塞 Redis 单线程，
   生产上是一次批量失效卡死整个系统的经典事故。实现走 `SCAN` 游标 + 去重。
3. **Caffeine 的计数器不参与前缀清理**：序列号被清掉会导致单号重复，这是绝对不能碰的
   （详见 §4.5 —— 这条注释救了后来的我）。

`DashboardCacheEvictor` 监听已有的 `ConsumeCompletedEvent`（`AFTER_COMMIT`）在结算/退单/充值
成功后主动失效，不需要新事件。

**验收证据**（round9）：预热后第二次读必须命中（`hits` 增长且载荷 `refreshTime` 不变）、
结算后下次读必须是 miss（缓存被失效）、`ttl=0` 时禁用且不累计命中、手动失效后能重新填充。

### 3.2 前端分包：3.1 MB → 2.36 MB

| | 改造前 | 改造后 |
|---|---|---|
| `dist` 总计 | ~3174 KB | **2360 KB** |
| 最大 chunk | 1246 KB | **942 KB**（`vendor-element`） |

### 3.3 类型错误 49 → 0

49 个错误全是同一个模式：Element Plus 表格作用域插槽给的是 `DefaultRow`，
直接传给业务类型参数报 `TS2322/TS2345`。

尝试过的路与结论：**类型化插槽在 vue-tsc 2.2 下不可行**（`<template #default="{ row }: { row: Row<T> }">`
在 SFC 编译后丢类型）。最终统一用「插槽形参 `any` + 处理函数内部收窄」，
把类型安全放在函数边界上而不是模板里。`round9` 断言 `vue-tsc --noEmit` 的 `error TS` 数为 0，
并把它作为回归门槛。

## 4. 第 4 批：多实例与限流（P2）

### 4.1 ShedLock：14 个任务加锁，以及「锁真的生效」怎么证明

改造前：pom 里有依赖、5 个 Job 类的注释都写着「多实例部署需启用 ShedLock」，
但**没有 `@EnableSchedulerLock`、没有任何 `@SchedulerLock`、也没有 `shedlock` 表** ——
系统事实上只能单实例部署。

改造：`SchedulerLockConfig`（`@EnableSchedulerLock(defaultLockAtMostFor="PT30M")` +
`JdbcTemplateLockProvider.usingDbTime()`）+ 全树 14 个定时任务补 `@SchedulerLock`
（用 `scripts/tools/add-scheduler-lock.js` 批量处理，`lockAtMostFor` 按各任务间隔单独定制）
+ Flyway V9 建表。

两个关键配置的理由：

- **`usingDbTime()`**：用数据库时间判定锁是否过期。默认用各实例本地时钟，实例间时钟漂移
  会让锁提前失效或永不释放 —— 分布式锁最经典的翻车方式。
- **`defaultLockAtMostFor=PT30M`**：持锁上限兜底。实例崩溃时锁不会永久占住
  （否则所有任务从此不再执行）。

**怎么证明锁真的生效**（这是 round10 §2 的设计）：表存在、字段对、有数据都只能证明
「表建对了」，不能证明「任务真的被锁住」。所以自检**从 JVM 外部抢锁**：

```
① 把 paySyncJob 的锁行改成 lock_until = 现在+180s，locked_by='round10-holder'
② 等 40 秒（该任务每 30 秒跑一次，必然尝试过）
③ 断言 locked_by 仍是 'round10-holder'  →  实例确实没能执行
④ 把 lock_until 改成过去时刻（模拟锁自然过期）
⑤ 断言 locked_by 变回实例名  →  任务恢复执行
```

第 ③ 步的**否定断言**才是关键：如果锁机制没生效，这一步会失败。

#### 4.1.1 实测发现的静默陷阱：表外删除锁行 = 该任务永久停摆

自检第一版第 ⑤ 步用的是 `DELETE FROM shedlock WHERE name=...`（模拟「清理锁表」），
结果任务**再也没恢复** —— 锁行明明不存在，应用却每 30 秒报一次「已被锁住」：

```
23:42:31 DEBUG DefaultLockingTaskExecutor - Not executing 'PaymentJob#paySyncJob'. It's locked.
23:43:01 DEBUG DefaultLockingTaskExecutor - Not executing 'PaymentJob#paySyncJob'. It's locked.
# 同时 SELECT COUNT(*) FROM shedlock WHERE name='PaymentJob#paySyncJob' → 0
```

反编译 `StorageBasedLockProvider` 后确认原因（不是猜的）：

```java
protected boolean doLock(LockConfiguration c) {
    String name = c.getName();
    // 内存表记住「这个名字的锁记录我已经 INSERT 过了」
    boolean canInsert = !lockRecordRegistry.lockRecordRecentlyCreated(name);
    if (canInsert) {
        if (storageAccessor.insertRecord(c)) { lockRecordRegistry.addLockRecord(name); return true; }
        lockRecordRegistry.addLockRecord(name);
    }
    return storageAccessor.updateRecord(c);   // 只有条件 UPDATE：WHERE name=? AND lock_until<=now
}
```

锁行被表外删除后：INSERT 路径被内存表跳过，条件 UPDATE 永远匹配不到行 →
**任务被永久判定为「已被锁住」而静默跳过，直到重启应用，且不产生任何错误日志。**

处置（已落地）：

1. **纠正自检的做法**：释放锁要「把 `lock_until` 推到过去」（走 UPDATE 路径，能匹配），
   而不是删行 —— 这也更接近真实场景（锁自然过期）；
2. **把这条陷阱写进代码注释**（`SchedulerLockConfig` 的类注释里写明「不要直接 DELETE」）；
3. **给出免重启的补救入口**：
   - `GET /api/admin/system/scheduler-locks` —— 看谁持着锁、持到什么时候、是否已过期；
   - `POST /api/admin/system/scheduler-locks/reset-cache` —— 调 `clearCache()` 清掉那份内存记忆，
     下一次调度会重新 INSERT，被删的行自愈；
4. **把它变成断言**（round10 §2b）：删行 → 断言任务确实停摆（把陷阱钉死，防止未来误判为
   「偶发」）→ 调 reset → 断言任务复活。三条断言同时证明了「陷阱存在」与「补救有效」：

```
[PASS] lock row deleted from outside                                   rows=0
[PASS] task stays skipped after an out-of-band delete (known ShedLock trap)  rows=0
[PASS] lock-memory reset accepted    provider=JdbcTemplateLockProvider
                                     remark=已清空本地锁记录记忆：下一次调度会重新 INSERT 锁行，被表外删除的行可自愈
[PASS] task revived after reset (no restart needed)                    locked_by=DESKTOP-1I7P2OQ
```

以及「真的被锁住」那一半（否定断言是关键）：

```
[PASS] lock held from outside the JVM                     holder=round10-holder until=2026-09-15 15:52:02
[PASS] instance did NOT run the job while the lock was held  holder=round10-holder   ← 40 秒内任务每 30 秒尝试过一次，没能执行
[PASS] job resumed once the lock expired                  locked_by=DESKTOP-1I7P2OQ
```

> 这条是「自检写不下去」逼出来的收获：如果第 ⑤ 步继续用 DELETE 并且我把断言改宽松，
> 这个陷阱就会以「偶发不恢复」的形态留在生产里，而它影响的是支付掉单补偿这类任务。

### 4.2 缓存就绪检测：把「静默不安全」变成「启动就喊」

`CacheService` 有两套实现，但缓存里放的不只是性能数据，还有**正确性数据**：
幂等键、登录失败计数、业务序列号、微信 access_token。多实例 + Caffeine 会让它们
**静默失效**（跨实例重复提交挡不住、锁定可绕过、两个实例可能生成相同单号）。

`CacheReadinessChecker` 做两件事：

1. **启动时**（`ApplicationReadyEvent`）检查并按需打 WARN —— 措辞刻意点明「静默失效」的后果，
   而不是「建议使用 Redis」这种没人会行动的话；
2. **管理端可查**：`GET /api/admin/system/cache-status` 返回
   `{cacheType, configuredType, multiInstance, multiInstanceSafe, risks[], suggestion}`。

配置口径也在这轮统一：**缓存实现由 `application.yml` 的 `member.cache.type` 决定，
不放 `m_sys_config`**（它在 Bean 创建前就已确定，放数据库会造成「改了没生效」的误解 ——
那种配置比没有更糟）。V9 里只保留 `cache.multi-instance` 这个**用于告警**的开关。
`CacheReadinessChecker` 的提示文案同步改成 `member.cache.type`，不再指向不存在的库内参数。

### 4.3 限流：固定窗口 + 维度区分 + 故障放行

`RateLimit` 注解 + `RateLimitAspect`：键 = `rl:{接口}:{主体}:{当前秒}`，
用 `CacheService.increment` 累加，超限抛 `ErrorCode.TOO_MANY_REQUESTS(10005)`
（这个错误码定义了却从未被使用，本注解是它的第一个消费方）。

覆盖范围（34 个端点）：

| 目标 | 粒度 | 额度 |
|---|---|---|
| 4 个小程序控制器（`/api/mp/**`，33 个端点） | 类级 `@RateLimit` | 20 次/秒/会员 |
| `POST /api/open/pay/notify/{channel}` | 方法级 `@RateLimit(dimension=IP, qps=100)` | 100 次/秒/IP |

四个设计决定：

1. **类级标注而不是逐方法**：小程序端整个控制器都是公网接口，逐个标注既啰嗦又容易漏
   （新增方法即裸奔）；
2. **维度区分**：会员登录后按会员 id 计数，未登录退化到 IP。同一门店 WiFi 下多个会员
   不该互相挤占额度；而回调是匿名接口，只能按 IP；
3. **限流优先级在幂等之外**（`@Order(50)` < 幂等的 100）：否则被刷的请求会先占用幂等键，
   用户稍后正常提交会拿到「请勿重复提交」—— 把「被刷」错误地表现为「你的操作有问题」；
4. **限流组件故障时放行**：缓存异常时记 WARN 并放行。限流是保护措施，不能因为保护措施
   故障让整个系统不可用（与「审计失败不能让收银失败」同一原则）。

**验收证据**（round10 §5/§6，实测数字）：连发 120 次 → **拦 101 / 过 19**
（必须出现 10005 且必须还有成功的，证明是「限流」而不是「全挡」）→ 等 2 秒后单次请求恢复
（证明窗口会滚动）→ 同一时刻的开放回调接口不受影响（证明不同接口各自计数）→
把 `ratelimit.enabled` 置 false 后 **120 次全过（拦 0）**、置回 true 后又出现拦 101 / 过 19。

### 4.4 切到 Redis 实测：13 条失败暴露的 5 个隐藏缺陷

§4.2 做完了「守卫」，但**切换路径本身一行都没跑过** —— 而 P2-2 的原话是
「Redis 是多实例部署的正确性前提」，一份没跑过的前提不能算完成。
于是本机装了一份便携 Redis（`tools/redis-8.10.1`，gitignored），
给 `run-all-tests.ps1` 加了 `-CacheType redis`（用命令行参数而不是环境变量：
local profile 里写死了 `member.cache.type: local`，**环境变量会被 profile 覆盖**），
然后跑全套自检 —— 结果 **549 / 13 FAIL**。

13 条失败全部指向 5 个根因，而且**其中 4 个在 Caffeine 下永远不会出现**
（Caffeine 存对象引用，不走 JSON 往返）：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 看板 9 项失败（`todayOrders=`、`liability=`、`levels=0`、`cache hits 1->1`） | 裸 `ObjectMapper` 没有 `JavaTimeModule` → 聚合结果里的 `LocalDateTime` 无法序列化 | 注册 `JavaTimeModule` + 时间写 ISO 字符串 |
| 2 | 微信支付 4 项失败（`private-key 无法解析：缓存值无法序列化为 JSON：RSAPrivateCrtKeyImpl`） | `PrivateKey` 是**接口**，JSON 无法还原类型 | 缓存里存 `算法:Base64(PKCS#8)`，读时还原 |
| 3 | （未直接失败，属潜在事故）平台证书读回来是 `LinkedHashMap` | `X509Certificate` 是抽象类，`Map<String,X509Certificate>` 读回来只是 Map | 改存 `序列号 → Base64(DER)`；否则回调验签抛 `ClassCastException`，表现为「回调一直验签失败」 |
| 4 | 每请求一条 WARN，一次自检刷出 **360 条**（`GrantedAuthority` 无法构造） | `LoginUser.getAuthorities()` 是派生视图且类型抽象；`enabled` 等只有 getter | `@JsonIgnore` 掉派生视图；mapper 关闭 `FAIL_ON_UNKNOWN_PROPERTIES`（滚动发布期间新旧实例共用缓存，字段增删不该让缓存整体失效） |
| 5 | 放大器 | **缓存写失败被冒泡成业务失败**（原设计「宁可抛错暴露」） | `set` 改为 WARN + 跳过：缓存是可选加速层，写不进去最多慢一点，绝不该让业务失败 |

第 2、3 条正好落在**支付**这条资金链路上 —— 也就是说，
如果不切一次后端，「补齐商户参数即可真实收款」这句话是没有依据的。

**为了让这一类问题不再靠运气发现**，round10 新增一节断言（§9）：
扫描后端日志，`值无法序列化为 JSON` / `反序列化失败` 必须为 **0 条**。
它拦得住上表 5 条里的 4 条 —— 加完这条断言后，带着未修复的 jar 再跑一次，
它精准地把第 4 条报了出来（`warnings=360`），第 5 次运行才全绿。

修复后的两种后端结果（**同一份 jar**）：

```
-CacheType redis ：executed = 564  |  TOTAL: PASS=564 FAIL=0
默认（Caffeine）  ：executed = 564  |  TOTAL: PASS=564 FAIL=0
```

切换手册、坑位清单与「上生产前还要补什么」见
[15-Redis切换与多实例](./15-Redis切换与多实例.md)。

### 4.5 本轮顺带修掉的两个隐藏缺陷

#### ① Caffeine 的计数器参数被忽略（限流会写爆内存）

```java
// 改造前：expireHours 参数完全没用上，注释里写的「日切自动清理」从未发生
private final ConcurrentHashMap<String, AtomicLong> counters = new ConcurrentHashMap<>();
public long increment(String key, long delta, long expireHours) {
    return counters.computeIfAbsent(key, k -> new AtomicLong(0)).addAndGet(delta);
}
```

原本只是「序列号键只增不减」（每天每业务一个键，量很小）。但限流的键是
**「每秒一个」**（`rl:{接口}:{主体}:{epochSecond}`）—— 一天就是 86400 个键/主体，
被刷时直接变成内存泄漏。**这不是性能问题，是能不能长期运行的可用性问题。**

修复：计数器改为有界 Caffeine 缓存 + **过期时刻记在值里**（每个键 TTL 不同：
序列号 48 小时、秒级序列 1 小时、限流 5 秒），超过阈值顺手清理已过期项。
**刻意不设统一的 `expireAfterWrite`**：序列号键要活 48 小时，统一 TTL 若短于它，
计数器会中途归零 → 单号重复。

同时给 `CacheService` 加了一个秒级重载 `increment(key, delta, timeout, unit)`：
小时粒度表达不了「1 秒窗口」，而 Redis 上每个限流键活 1 小时意味着单主体 3600 个键。

#### ② 方法级 `@RateLimit` 绑定到 `null`（支付回调 90001）

```java
// 改造前
@Around("@annotation(rateLimit) || @within(rateLimit)")
public Object around(ProceedingJoinPoint pjp, RateLimit rateLimit) {
```

小程序端（类级注解）限流正常，但方法级注解的支付回调直接抛：

```
java.lang.NullPointerException: Cannot invoke "RateLimit.key()" because "rateLimit" is null
```

即**切点匹配上了、形参却是 null**。后果是「支付回调全部返回 90001」——
限流没生效，回调还坏了（真实渠道会当成失败并重试）。这与 §1.2 的
`inconsistent binding` 是同一类问题：**不要让切点去绑定注解实例**。

修复：切点只按注解类型匹配（`@within(...RateLimit) || @annotation(...RateLimit)`），
通知内部先取方法注解、再取声明类注解（`getMethod().getDeclaringClass()`，
不能用 `getDeclaringType()` —— 后者返回 AspectJ 裸 Class，拿不到注解）。
round10 里保留了一条对开放回调的断言，专门防止它再坏。

### 5.2 新增哨兵：声明断言数 == 实际执行数

`run-all-tests.ps1` 现在会读 `ensure-bom.js --json` 的「每套脚本声明了多少条 `Check`」，
与每套实际跑出的 `PASS+FAIL` 逐套比对，不等即判 FAIL 并在汇总里点名。

**为什么必须有这条**：断言消失是静默的，脚本依旧打印「全绿」。

### 5.3 一次真实的「断言静默消失」事故复盘

round10 第一次跑出来是 `PASS=18 FAIL=16`，看起来只是「新写的自检有问题」。但声明数是 36，
实际执行 18+16=34 —— **有 2 条断言根本没执行，也没报错**。

原因链条：

```powershell
# ① 这台 mysql 客户端没有指定库 → 报 "No database selected"
$out = & $mysql ... -e $q
# ② [int] 转换错误文本 → 抛「语句级终止错误」
Check 'V9 migration applied' ([int](Sql "...") -eq 1) 'v9'
# ③ $ErrorActionPreference='Continue' 不会终止脚本，但这一条语句被终止
#    → Check 从未被调用 → PASS/FAIL 都不增加 → 汇总看起来只是「少了几条」
```

同一批里还有两个更隐蔽的连带后果：

- `information_schema` 查询里的 `DATABASE()` 在未选库时是 `NULL`，于是「表存在吗」
  这类断言会返回 0 而不是报错 —— **不报错但答案是错的**；
- 有的断言「通过」了：`$mpQps -ne ''` 里的 `$mpQps` 是那句错误文本，
  非空即通过 —— **为了错误的原因而通过**。

修复：① `Sql` 显式带库名；② 新增 `SqlInt`（`[int]::TryParse`），
让查询失败变成可见的 FAIL 而不是消失的断言。

于是有了 §5.2 的哨兵：**只要「声明数 ≠ 执行数」，无论输出多绿都判失败。**
