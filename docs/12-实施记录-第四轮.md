## 0. 本轮起因：表拆了，功能没拆

第一轮建表时就已经把「员工」和「登录账号」分成两张表（`m_staff` 与 `m_sys_user.staff_id`），
菜单 1101/1102/1103（门店管理/员工管理/业绩排行）也早已定义。但**一直没有对应的代码与页面**：

| 检查项 | 修复前 |
|---|---|
| `m_staff` 表 | ✅ 存在（工号/姓名/岗位/入职离职/在职状态） |
| `m_sys_user.staff_id` | ✅ 存在 |
| `Staff` 实体 / Mapper / Service / Controller | ❌ 全都没有 |

| WEB 员工/门店/业绩页面 | ❌ 三个菜单都是死链 |
| 引用 `staff_id` 的地方 | 只有 `m_order.staffId` 与报表里的 `staffRanking` |

代班时业绩串人，员工离职后自己的业绩再也查不到。

## 1. 核心设计：两条独立的生命周期

这是本轮唯一重要的事，其余都是配套。

```
员工离职（leave）      → m_staff.status=0 + leave_date
                        账号一动不动
                        返回提示「该员工仍有启用中的账号，建议一并停用」

账号停用（系统管理）    → m_sys_user.status=0
                        员工档案一动不动

员工复职（reinstate）  → status=1、清 leave_date
                        原关联账号的可用性由账号自己的状态决定
```

### 1.1 为什么不自动联动

看起来「离职就自动停账号」更省事，但真实门店里这两件事经常不同步：

- 员工离职当天还要用账号做交接、退押金、结清挂单；
- 财务、运营岗可能压根没有员工档案（不是门店的人），停谁去？
- 反过来，账号可能因为「密码疑似泄露」被临时停用，人还在正常上班。

自动联动会制造「**账号被系统悄悄停掉，人却还在上班**」这类现场事故，
而它极难被发现 —— 直到收银台登不上去。

因此系统只做**提示**，把决定权留给人。为此后端在两个方向都算好了告警文案：

| 情况 | 系统给出的告警 |
|---|---|
| 员工在职 + 账号停用 | 「员工在职，但关联账号已停用，该员工将无法登录」 |
| 员工离职 + 账号启用 | 「员工已离职，但关联账号仍可登录，建议停用」 |

员工列表与详情直接展示这两条，运营不需要自己去对照两张表。

### 1.2 离职绝不删记录

`m_order.staff_id` 指向 `m_staff`。删掉员工 → 历史订单的业绩归属变成悬空外键 →
报表里那个人凭空消失。所以：

- 离职只置 `status=0` + 记 `leave_date`；
- 连**逻辑删除都会被拒绝**（只要有任何业绩）：

```
该员工有 N 笔历史业绩，不能删除；请改为「办理离职」，以保留业绩归属
```

只有从未产生过业绩的员工（建错的、录错的）才删得掉。

### 1.3 账号关联是「可选的一对一」

```
可以有员工没账号   → 新人还没开号
可以有账号没员工   → 纯运营/财务岗
一个员工最多一个账号，一个账号最多挂一个员工
```

约束由 `SysUserMapper.bindStaff` 的条件 UPDATE 兜底：

```sql
UPDATE m_sys_user SET staff_id = #{staffId}
 WHERE id = #{userId} AND deleted = 0 AND (staff_id IS NULL OR staff_id = #{staffId})
```

并发下两个请求同时抢绑同一个账号，只有一个能改成功，另一个影响 0 行并拿到明确报错。

关联时若账号还没有默认门店，顺手同步成员工所属门店 —— 否则该账号的数据权限会落在空门店上，
「本店」范围的查询全都查不到东西。

## 2. 业绩归属：从「账号」改回「员工」

### 2.1 报表口径修正

`DashboardService.staffRanking` 原本是这样的：

```sql
-- 修复前：按登录账号统计
SELECT o.cashier_id, u.real_name AS staff_name, ...
  FROM m_order o LEFT JOIN m_sys_user u ON u.id = o.cashier_id
```

改为：

```sql
-- 修复后：按员工统计
SELECT s.id AS staff_id, s.staff_no, s.staff_name, s.position, s.store_id, ...
  FROM m_order o JOIN m_staff s ON s.id = o.staff_id AND s.deleted = 0
 WHERE o.status IN (3,4) AND o.staff_id IS NOT NULL
```

时间口径同时从 `created_at` 换成 `paid_at`：业绩应以「钱什么时候收到」为准。
正常结算下两者只差毫秒（同一事务内写入），所以不会与看板其它指标打架。

### 2.2 结算时补一道回落（防业绩永久丢失）

`m_order.staff_id` 此前完全依赖前端传值 —— **前端漏传就永久丢失归属，事后无法补**。

`CashierService.resolveStaffId` 现在：优先用显式传入的 `staffId`（收银台选人、代班场景），
未传时回落到「当前登录账号所绑定的员工」。

刻意**不校验**传入的 staffId 是否属于当前门店：连锁门店常有跨店支援，
强行限制会把真实业务挡在门外。归属是否合理，由「业绩排行」的门店筛选去发现。

### 2.3 业绩口径（避免和财务报表打架）

| 项 | 口径 |
|---|---|
| 计入的订单 | `status IN (3,4,5)` 即「曾经支付成功过」 |
| 退款处理 | 部分/全额退款的订单**仍计入业绩**，退款金额单独列出，不做净额扣减 |
| 不计入 | 挂单（7）、未支付（1/2）、已取消（6） |
| 客单价 | 实付金额 / 订单数 |

**为什么不做净额**：「卖出多少」和「退了多少」是两个可分别核对的数；
混成一个净额后，一旦有人问「这个数怎么来的」就无法解释。

## 3. 门店：数据权限的锚点

门店被订单、会员、员工、用户（默认门店）四方同时引用，因此**几乎永远不该被删除**。

`StoreService.remove` 做引用盘点，任一存在即拒绝，并明确告诉运营该去处理什么：

| 引用方 | 提示 |
|---|---|
| 在职员工 | N 名在职员工 |
| 离职员工档案 | N 名离职员工的档案 |
| 历史订单 | N 笔历史订单 |
| 归属会员 | N 名归属会员 |
| 默认门店账号 | N 个默认门店为该店的账号 |

> 这一条是本轮自查时补上的：最初只挡「在职员工」，结果测试数据里出现了
> 「门店已删除，但离职员工的 `store_id` 仍指向它」的悬空引用。
> 参照「有业绩的员工不能删」的同一原则，改成了全引用盘点。

只有**刚建错、还没被任何数据引用**的门店才删得掉。列表接口直接返回
`deletable` 与 `deleteBlockReason`，前端据此禁用删除按钮并 hover 显示原因 ——
而不是让用户点下去才报错。

## 6. 本轮踩到的坑

### 6.1 `Field 'created_at' doesn't have a default value`

`m_store.created_at` 是 NOT NULL 且无默认值，而 `Store` 实体的 `createdAt`
**没有 `@TableField(fill = FieldFill.INSERT)`**。因为此前从没有代码插入过门店，
这个注解缺失一直没暴露，直到本轮实现门店新增才炸。

报错来自 JDBC 驱动，信息里**不会告诉你「是你实体少了个注解」**，只说要给值。

**处理**：补 `fill` 注解；并顺手写了一次全实体扫描（`createdAt` 是否声明 `fill`），
发现 `LoginLog` 也有同样问题 —— 它碰巧能用，是因为 `LoginLogService` 每次
都记得显式 `setCreatedAt(now())`。这种「靠调用方记得」的约定迟早会漏，
一并补上注解。

### 6.2 `m_staff.store_id` 是 NOT NULL —— 门店必填

`StaffSaveCmd.storeId` 原本是可选的，插入时报 `Field 'store_id' doesn't have a default value`。

这不是 bug 而是**设计本意**：门店是数据权限锚点，一个不属于任何门店的员工，
其账号的数据权限会落在空门店上，「本店」范围的查询全都查不到东西。

**处理**：`storeId` 改为 `@NotNull`，并在服务层前置校验「门店存在且未删除」，
把数据库层的天书报错换成「所属门店不能为空」/「所选门店不存在或已删除」。
连锁总部的员工请挂在总部门店。

### 6.3 又一次被 .ps1 的 BOM 咬到

`round6-test.ps1` 写入后没有 BOM（写文件的工具默认输出 UTF-8 无 BOM），
PowerShell 5.1 按 ANSI 解析时，中文字符串末尾字节吃掉换行，**语法直接坏掉**：

```
Unexpected token 'status=' + $newStore.data.status)
```

这正是 [11-实施记录-第三轮 §9.5](./11-实施记录-第三轮.md) 记录过的机制。
这次**在跑之前就被 `scripts/tools/ensure-bom.js` 拦下了** ——
第三轮加的守卫起作用了，从「事后排查两小时」变成「一条命令修好」。

登录 http://127.0.0.1:5173 （`admin` / `Admin@123`），左侧 **门店与员工** 分组：

- **门店管理** —— 建店、设店长、停业；被引用的门店删除按钮会置灰并说明原因
- **员工管理** —— 建员工（工号自动生成）、关联账号、办离职；
  离职后账号仍可登录，列表会提示「建议停用该账号」
- **业绩排行** —— 按员工归属的业绩，支持门店与日期筛选，可下钻看日趋势与支付方式构成
