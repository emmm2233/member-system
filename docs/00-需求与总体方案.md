# 会员管理系统 · 需求与总体方案

> 版本：v1.0（设计稿）｜ 日期：2026-09 ｜ 状态：**待评审**
>
> 技术基线：微信小程序端 + WEB 管理端 ｜ 前端 Vue 3 ｜ 后端 Spring Boot 3 ｜ 数据库 MySQL 8
>
> 关键决策：**通用型会员模型（储值卡 + 等级 + 积分）**；**不接入线上支付，只做线下收银记账**

---

## 1. 项目定位

面向**单品牌多门店**的实体经营场景（餐饮、美业、洗车、健身、零售、母婴等），提供：

- **一套会员资产体系**：储值余额、赠送余额、积分、成长值、等级、标签、优惠券
- **一个收银记账闭环**：充值、消费、退款、积分调整、次卡核销，全部留痕可追溯
- **两端协同**：小程序端服务会员自助（查余额/账单/券/预约/核销码），WEB 管理端服务店员与管理者（收银、发券、看板、权限）
- **一套可扩展的营销引擎**：等级权益、生日礼、推荐有礼、券模板、活动规则以「配置 + 规则表」驱动，不写死在代码里

### 1.1 设计原则

1. **账实相符优先**：一切资产变动（余额/积分/成长值/券）必须生成不可变流水，任一时点余额可由流水重算校验。
2. **幂等防重**：所有资金与资产变动接口必须携带幂等键，杜绝重复扣款/重复送券。
3. **规则可配**：等级门槛、积分规则、券规则、推荐奖励全部落表，运营改规则不改代码。
4. **金额零误差**：金额统一用 `DECIMAL(12,2)` / Java `BigDecimal`，**禁止 double**；事务内变动 + 行锁。
5. **前后端分离**：统一 REST 风格，统一响应体与错误码，两端共用同一套后端接口（按端区分鉴权与数据范围）。

## 2. 业务模型

### 2.1 四类资产

| 资产 | 载体 | 获取方式 | 消耗方式 | 是否有有效期 |
|---|---|---|---|---|
| **储值余额**（本金） | `m_member_account.balance` | 线下现金/扫码充值 | 消费抵扣、退款 | 无（可配置） |
| **赠送余额** | `m_member_account.gift_balance` | 充值赠送、活动、推荐奖励 | 消费时按比例/优先抵扣 | 可配置 |
| **积分** | `m_member_account.points` | 消费、充值、生日、活动 | 兑换商品/券，或抵扣 | 有（默认滚动 12 个月过期） |
| **成长值** | `m_member_account.growth` | 消费金额换算（剔除赠送抵扣部分） | 只用于等级判定 | 无（可配置年度清零） |

> **本金与赠送分离**是核心设计：退款只退本金、赠送不退；报表中"储值负债"只统计本金；避免"充 1000 送 1000 再退款套现"的资金风险。

### 2.2 会员等级模型（升级 / 保级 / 降级）

| 维度 | 规则 |
|---|---|
| 等级数量 | 默认 5 级（普通/银卡/金卡/铂金/黑金），可增删 |
| 升级依据 | `累计成长值` / `累计实付金额` / `累计消费次数`，三选一或组合（规则表配置） |
| 升级方式 | **实时计算**：每次消费后比对门槛，达标即升级并写等级变更日志 |
| 保级/降级 | 支持「有效期制」：等级设 `valid_months`，到期后按保级条件（近 N 月消费额）重新评定；默认关闭降级 |
| 等级权益 | 折扣率、积分倍率、生日礼、专属券包、次卡折扣、是否免最低充值额 |

### 2.3 会员卡（权益卡）模型

- **储值卡**：无固定面额，会员账户即卡；可设开卡礼。
- **次卡 / 服务卡**：一次性购买"10 次洗车""5 次护理"，落 `m_member_card` + `m_member_card_item`，核销一次扣一次，支持有效期与冻结。
- **权益卡（付费会员）**：购买后 N 天内享折扣/免配送费等（本期做轻量版：等价于发一张长有效期的大额折扣券包）。
- 会员与卡：一个会员可持多张卡，一卡一账户，**账户余额与卡绑定**（默认主卡账户）。

### 2.4 优惠券模型

| 类型 | 说明 | 计算方式 |
|---|---|---|
| 满减券 | 满 X 减 Y | 定额扣减 |
| 折扣券 | 打 N 折（可设封顶优惠额） | 按比例 |
| 代金券 | 无门槛抵扣 Y 元 | 定额 |
| 兑换券 | 免费兑换指定商品/服务 | 抵扣金额=商品原价 |
| 次卡券 | 含 N 次权益 | 转成次卡 |

关键约束：`适用门店范围` / `适用商品范围` / `最低消费` / `有效期（绝对或领取后 N 天）` / `每人限领` / `发行总量` / `是否可叠加`。

### 2.5 收银场景（线下记账，不接线上支付）

支持三种"支付方式"记账，均不经过第三方支付网关：

| 支付方式 | 说明 | 资金流 |
|---|---|---|
| `BALANCE` 储值余额 | 从会员账户扣减 | 写余额流水，减少储值负债 |
| `CASH` 现金 | 店员收取现金 | 写订单实收，计入门店营收 |
| `OFFLINE_CODE` 线下扫码 | 顾客扫店内收款码（微信/支付宝/银行码），店员确认到账后记账 | 写订单实收 + 外部交易号（人工填/可选拍照） |
| `MIXED` 组合支付 | 余额 + 现金/扫码混合 | 多条支付明细 |
| `WECHAT_ONLINE` 微信在线支付 | **预留**：小程序内自助充值/购卡时调起微信支付，结果由回调驱动入账 | 支付单 → 回调 → `AccountService` 入账（与线下链路复用同一入账逻辑） |

> **支付网关抽象（已落地为接口设计）**：`IPayChannel` + 渠道实现注册表。本期实现 `MockPayChannel`（开发/测试可全流程跑通），并**预留下单、查单、关单、退款、回调解析、回调验签**六个方法签名与支付单表结构；商户号与证书到位后新增 `WechatPayChannel` 即可切换，业务代码零改动。详见 [01-系统架构设计 §6](./01-系统架构设计.md) 与 [03-接口设计 §12](./03-接口设计.md)。

### 2.6 微信能力使用范围

| 能力 | 用途 | 本期 |
|---|---|---|
| `wx.login` → `code2Session` | 小程序静默登录换 openid/unionid | ✅ |
| 手机号快速验证（`getPhoneNumber`） | 绑定手机号，作为会员唯一识别之一 | ✅ |
| 订阅消息 | 消费/充值到账、积分变动、券到期、生日礼、次卡到期提醒 | ✅（模板 ID 配置化） |
| 小程序码 | 会员核销码、推荐海报二维码、门店码 | ✅ |
| 微信支付 | 小程序内**在线充值 / 购卡**（JSAPI 下单、支付回调入账、原路退款） | 🟡 **接口与表结构已预留**：`IPayChannel` 抽象 + 支付单表 + 回调日志表 + 小程序支付接口 + 前端支付流程全部设计到位；`MockPayChannel` 可跑通全流程，真实商户号到位后补 `WechatPayChannel` 实现即可上线 |
| 微信开放平台 UnionID | 多小程序/公众号打通 | ✅（有则用，无则降级为 openid） |

### 2.7 多门店模型

- `m_store` 为最小经营单元；**每个门店有独立的收银员、货品/服务价目、业绩归属**。
- 默认**通店通用**：余额、积分、券可在任意门店使用（受券的适用门店限制）。
- 等级规则、券模板、活动由**总部统一配置**；门店可见自己的会员与流水（数据权限 `DATA_SCOPE`）。
- 员工业绩：订单记 `cashier_id`（收银员）+ `store_id`（业绩门店）。

## 5. 非功能需求

| 类别 | 指标 / 要求 |
|---|---|
| 性能 | 单接口 P95 < 300ms；收银结算接口 P95 < 500ms；支持 500 并发在线店员、日订单 5 万 |
| 容量 | 会员 100 万、流水 5000 万（按月分表预留，本期单表 + 索引优化 + 归档任务） |
| 一致性 | 资金类操作 `@Transactional` + 悲观行锁（`SELECT ... FOR UPDATE`）+ 幂等键；每日 T+1 对账任务校验「余额 = Σ流水」 |
| 安全 | 密码 BCrypt；JWT 双 token（access 2h / refresh 7d）；接口签名与限流；敏感字段（手机号）脱敏展示 + 导出需二次确认；防重放（nonce）|
| 审计 | 所有资产变动、权限变更、退单、导出操作写操作日志（操作人/IP/前后值/原因）|
| 可用性 | 单机可跑；生产建议 Nginx + 双实例 + Redis 哨兵 + MySQL 主从 |
| 兼容 | 微信小程序基础库 ≥ 2.30；WEB 支持 Chrome/Edge 90+、iPad Safari，收银页做 Pad 大按钮适配 |
| 可维护 | 统一响应体/错误码；Flyway 管理 DDL 版本；Swagger/OpenAPI 自动文档；日志分级与 traceId |
