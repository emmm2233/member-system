### 2.1 后端命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| Controller | `XxxController`，只做校验与转换 | `MemberController` |
| Service | 接口 `XxxService` + 实现 `XxxServiceImpl` | `AccountServiceImpl` |
| Mapper | `XxxMapper`（+ `XxxMapper.xml`） | `MemberAccountMapper` |
| Entity | `Xxx`（对应表去掉 `m_` 前缀） | `MemberAccount` |
| DTO | `XxxCmd`（写）/ `XxxQuery`（查） | `RechargeCmd` |
| VO | `XxxVO` / `XxxDetailVO` / `XxxPageVO` | `MemberDetailVO` |
| 转换 | `XxxConvert`（MapStruct） | `MemberConvert` |
| 方法 | 动词开头：`create/get/page/update/remove/change/verify/grant` | `verifyCoupon` |
| 表字段↔Java | 蛇形 ↔ 驼峰自动映射 | `gift_balance` ↔ `giftBalance` |

### 2.2 编码铁律（Code Review 必查）

1. **金额只用 `BigDecimal`**，禁止 `double`/`float`；比较用 `compareTo`，不用 `equals`。
2. **资产变动只能经 `AccountService`**，其他模块禁止直接 update 账户表。
3. **事务方法内禁止远程调用**（微信、HTTP），统一 `afterCommit` 事件或异步。
4. **所有写接口带幂等**（资金类强制 `@Idempotent`）。
5. **列表查询必须分页**，禁止无 limit 查询；导出走异步任务。
6. **Entity 不出 Controller**，必须转 VO；敏感字段（手机号）默认脱敏。
7. **操作日志注解覆盖**：资产变动、退单、权限变更、配置修改、导出。
8. **异常统一抛 `BizException(ErrorCode)`**，不吞异常、不返回 null 表示失败。
9. **SQL 不用 `SELECT *`**，明确列名（避免表结构变更导致意外）。
10. **新增配置项落 `m_sys_config`** 并在 `02-数据库设计.md` 同步，禁止硬编码业务阈值。
11. **支付相关代码只依赖 `IPayChannel` 接口**，禁止在业务代码里出现 `WechatPayChannel` 之类的具体实现引用（渠道通过注册表按配置查找）；密钥只从环境变量读取，禁止入库出仓。
12. **入账只有一个入口**：无论线上支付回调、主动查单补偿、还是收银员手工充值，最终都必须调用 `AccountService.recharge`；禁止为在线支付另写一套入账逻辑。

## 3. WEB 管理端工程结构（`web-admin/`）

详见 [04-前端页面与路由设计 §4](./04-前端页面与路由设计.md)。要点：

| 项 | 约定 |
|---|---|
| 命名 | 组件 `PascalCase.vue`；页面目录小驼峰 `memberList/`；工具 `camelCase.ts` |
| 类型 | 每个接口出入口都有 TS 类型，放 `src/types/`，与后端 DTO 字段名一致（camelCase） |
| 请求 | 只在 `api/*.ts` 发请求，页面不直接调 axios |
| 状态 | 跨页面共享用 Pinia；页面内状态用 `ref/reactive` |
| 权限 | 路由 `meta.perm` + 按钮 `v-perm`；无权限不渲染（不是禁用） |
| 金额 | 计算用 `decimal.js`，展示统一 `AmountText` |
| 幂等 | 收银/充值/退单等写操作统一 `useIdempotency()` |

## 5. 本地开发环境搭建

### 5.1 前置依赖

| 依赖 | 版本 | 本机现状 | 处理 |
|---|---|---|---|
| JDK | 21 | ✅ 已装 21.0.11 | — |
| Maven | 3.9+ | ❌ 未装 | **用 `mvnw` 包装器**（随仓库提供）或安装 Maven / 用 IDE 内置 |
| MySQL | 8.0.35+ | ❌ 未装（无 mysql 客户端） | 用 Docker 起，或安装 MySQL 8 安装版 |
| Redis | 7.x | 未知 | 用 Docker 起（Windows 原生版可选 Memurai/Redis for Windows） |
| Node.js | 20/22+ | ✅ v24.14.1 | — |
| pnpm / npm | 最新 | 需确认 | 建议 `npm i -g pnpm` |
| Docker Desktop | 最新 | 需确认 | 用于 mysql/redis，可选 |
| 微信开发者工具 | 最新稳定版 | 需确认 | 小程序端调试必需 |

### 5.2 一键启动（目标形态）

```powershell
# 1) 起依赖（MySQL + Redis）
cd deploy
docker compose up -d mysql redis

# 2) 初始化数据库（compose 已挂载 sql/ 到 /docker-entrypoint-initdb.d 时自动执行）
#    手动执行方式：
docker exec -i member-mysql mysql -uroot -p123456 < ..\sql\V1__init_schema.sql

# 3) 起后端
cd ..\backend
.\mvnw.cmd spring-boot:run -Dspring-boot.run.profiles=local
#    → http://localhost:8080   Swagger: http://localhost:8080/swagger-ui.html

# 4) 起 WEB 管理端
cd ..\web-admin
pnpm install
pnpm dev
#    → http://localhost:5173   （默认账号 admin / Admin@123）

# 5) 小程序端：用微信开发者工具打开 mp-member/dist/dev/mp-weixin
cd ..\mp-member
pnpm install
pnpm dev:mp-weixin
```

## 6. 编码实施顺序（每个阶段都可独立验收）

| 阶段 | 交付内容 | 依赖 | 验收标准 |
|---|---|---|---|
| **P0 骨架**（3d） | 后端骨架 + Flyway V1 全量 DDL + 统一响应体/异常/日志/幂等切面 + JWT 登录 + Swagger；WEB 骨架（布局/路由/请求封装/登录页/动态菜单）；docker-compose | 环境 | 能登录进后台并看到菜单；`V1__init_schema.sql` 执行后 45 张表齐全 + 初始化数据可查 |
| **P1 会员与资产**（5d） | 会员 CRUD/列表筛选/详情 360°、标签、账户查询、余额/积分流水、充值（含赠送送券）、充值撤销、资产调整、导入导出 | P0 | T01 通过；充值幂等与并发测试通过；会员列表 1 万条数据分页 < 300ms |
| **P2 收银闭环**（6d） | 商品/分类/充值方案、收银台页面（会员识别/购物车/用券/积分/组合支付）、结算接口、订单查询与详情、退单审批、次卡售卡与核销、交班、小票打印 | P1 | T02/T03/T04/T10/T15 通过；收银页 Pad 可用；金额与流水对账无差异 |
| **P3 等级与积分**（4d） | 等级定义与规则构造器、等级评定（实时+定时）、升级礼、积分规则、积分商城与兑换、积分过期任务与提醒 | P2 | T07/T08 通过；规则误配可通过"模拟测算"提前发现 |
| **P4 卡券营销**（6d） | 券模板（含预览）、发券向导（定向/条件/批量）、券核销与撤销、券锁定、领券中心、推荐有礼、生日礼 | P2 | T05/T09/T11/T14 通过；券并发安全；批量发券 3000 人 < 30s |
| **P5 小程序端**（6d） | 登录/绑定手机号、首页、钱包、账单、卡券、次卡、核销码、积分商城、推荐有礼、资料、消息、门店 | P1~P4 接口 | 全流程真机跑通：注册→绑手机→领券→到店核销→查看账单 |
| **P6 看板与系统**（5d） | 看板与报表（含 RFM/留存）、导出任务、RBAC 完整（用户/角色/菜单/数据范围）、字典、参数、消息模板、定时任务管理、操作与登录日志 | P1~P5 | 各角色登录看到的菜单与数据范围正确；报表数字与明细可核对 |
| **P7 联调加固**（4d） | 压测与优化、对账任务上线、异常告警、归档任务、部署文档、操作手册、数据初始化脚本 | 全部 | T12 通过；压测达标（P95 < 300ms，收银 < 500ms）；部署文档可复现 |
| **P8 支付接入**（预留 3~4d） | 真实微信支付上线：`WechatPayChannel` 实现（APIv3 下单/查单/关单/退款/回调验签与解密）、商户证书与环境变量配置、`PaySyncJob`/`PayCloseJob`/`PayReconcileJob` 上线、真机联调、支付对账核对 | P5 + 商户资质 | T16~T20 通过；**以 0.01 元真机实测全链路**；回调验签与重放测试通过；支付对账无差异 |

> **P8 的启动前提**（当前均未就绪，故本期只落地接口与表结构）：
> ① 微信商户号（普通商户/服务商）已开通且与小程序 AppID 完成绑定；
> ② APIv3 密钥、商户私钥与证书序列号已生成；
> ③ 小程序已完成微信认证（未认证无法调起支付）；
> ④ 回调地址为公网 HTTPS。
>
> **P8 不需要改动的部分**：数据库表、业务入账逻辑、小程序页面、管理端页面 —— 全部在 P0~P7 已按本设计预留完毕。

**总计约 39 人日**（1 人全职，不含 P8 支付接入的 3~4 人日）；若前后端并行（2 人），可压缩到约 22~25 个工作日。

## 7. 风险登记册

| # | 风险 | 影响 | 概率 | 应对 |
|---|---|---|---|---|
| R1 | 资金台账出现差异（余额≠流水） | 高——信任崩塌 | 中 | 三层幂等 + 行锁 + T+1 对账 + 差异告警 + 调账留痕 |
| R2 | 需求蔓延（不断加功能） | 中——工期失控 | 高 | 本期范围明确（00 文档 §7 不做清单）；新需求进 P8+ 排期 |
| R3 | 微信订阅消息需用户主动授权，触达率低 | 中——提醒效果差 | 高 | 关键动作用一次性订阅 + 站内消息兜底；后续可加短信通道 |
| R4 | 线下记账缺少支付凭证，易产生纠纷 | 中 | 中 | 线下扫码需填外部流水号/可拍照留证；退单必填原因 + 审批 |
| R5 | 大表（流水/订单）查询变慢 | 中 | 中 | 索引 + 游标分页 + 归档任务；数据量到阈值再评估分区 |
| R6 | 规则引擎配置错误导致批量误升级/误发券 | 高 | 中 | 规则保存前"模拟测算"；批量操作二次确认 + 操作日志 + 可回滚（等级变更日志支持回退） |
| R7 | 小程序审核被驳回 | 低——延迟上线 | 中 | 提前准备隐私协议/授权说明；先提交体验版验证 |
| R8 | 收银台依赖网络，断网无法收银 | 中 | 中 | 交互上保留购物车不清空；后续可评估 PWA/本地缓存离线开单 |
| R9 | 本机无 Maven/MySQL 环境 | 低——开发受阻 | 高 | 提供 mvnw 包装器 + docker-compose；或在 P0 阶段先安装环境 |
| R10 | 单人开发无 Code Review | 中——质量问题 | 中 | 资金逻辑写单测自证；关键逻辑（扣减/幂等/对账）单独走查 |
| R11 | 支付回调不可达（无公网 HTTPS / 未备案域名） | 中——在线支付上线延期 | 中 | 本期只预留不启用（`pay.enabled=false`）；P8 前先确认域名与证书；本地用 Mock 渠道联调 |
| R12 | 微信支付证书/APIv3 密钥轮换或过期导致支付失效 | 高——会员无法在线充值 | 低 | 平台证书自动下载 + 证书到期前 30 天告警；`PaySyncJob` 与对账任务能第一时间发现异常 |
